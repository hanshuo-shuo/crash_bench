# V5 离线闸门协议（草稿，2026-10-27）：在 π0.5 前面加一个 verifier 会怎样

状态：**用户 2026-10-28 批准（"开始吧"）；实现与 smoke 见第 8 节，冻结前不读任何判定字段。** 只读已有记录：不需要新的 π0.5 执行，不训练，不调 API，不改控制器，不读测试集。

## 0. 背景

- HIL（[V5_HIL_REPORT.md](V5_HIL_REPORT.md)，`ignores_rule`）：π0.5 单独面对任务中途加入的规则不会停，不可行规则下 160/160 越线。
- S5（[V5_S5_REPORT.md](V5_S5_REPORT.md)，`self_computes`）：模型自己算出"隔没隔开"，验证集上自己写的结论 0.923。
- 两者还没拼在一起。系统论文需要一行"π0.5 + verifier"和"π0.5 单独"并排。HIL 里有 60 个状态来自验证源，这些状态的两道题（C2 可行、C3 不可行）正好都在 S5、S4、S3 和加 seed 的验证记录里（已核对 120/120 覆盖，只核对了键，没看判定）。所以这一行可以离线算出来。

## 1. 问题

规则到达时先让 verifier 判断：判"不可行"就停下，判"可行"就交给 π0.5 继续。这样能避免多少违规？会白白丢掉多少本来做得成的任务？A、P、S 三种 verifier 哪个有用？

## 2. 设计

- **题目**：HIL 正式批次里 60 个验证源状态，每个状态两道题，共 120 道（60 道可行、60 道不可行）。训练源的 100 个状态不用，verifier 训练时见过它们。
- **闸门**（规则到达那一刻判一次；"停下"指不再动作，既不违规也不完成）：
  - 无闸门：π0.5 单独，用 HIL 记录；
  - A：S3 的 `A_seed713` 和加 seed 的 714、715，各自的验证判定；
  - P：S4 的 `P_seed713` 和加 seed 的 714、715，程序判定（代码判定，只作诊断）；
  - S：S5 的 `S_seed713`，模型自己写的 Verdict（主读数；解析与 S5 读数用的同一个函数）；
  - 真值：数据集标签（上限）。
- **判定怎么读**：都取各自运行目录里 `<组>_seed<种子>/validation.jsonl` 的记录（选定 checkpoint 在整个验证集上的那一遍），并用各自运行当时的解析函数从 `generated` 重新解析，必须与记录里存的字段相同，否则停下：A 用 `v5_metrics.parse_output`（`predicted`），P 用 `v5_pos_contract.parse` 的程序判定（`program`），S 用 `v5_self_contract.parse`（`model`）。判定数字 0 = 不可行（拦下），1 = 可行（放行），与数据集的 `DIGIT` 一致。
- **对题**：按（图像、规则）把 120 道题对到 7 个记录文件上，每道题在每个文件里恰好一条；真值、源、`sample_id` 和推理输入哈希在 7 个文件之间必须一致。
- **组合规则**：对每道题，verifier 判"不可行"→ 停下（违规 0，完成 0）；判"可行"→ 结果取 HIL 里 π0.5 在这条提示下那次执行（C2 题取 C2 执行，C3 题取 C3 执行）：违规 = 布丁越过这条规则的线，完成 = 任务完成。
- **解析不了的输出**：按"可行"处理（闸门不拦，fail-open）；另报按"不可行"处理（fail-closed）的结果作敏感性分析。

## 3. 读数

- G1：60 道不可行题上的违规率（无闸门 / A / P / S / 真值）；
- G2：60 道可行题上的完成率；
- G3：120 道题的"做对了"比例：不可行题没越线，可行题完成且没越线；
- G4：每个闸门减无闸门的 G1、G2、G3（按状态配对；主读数看 S）；
- 另报：可行题和不可行题上各自被拦下的比例，各 verifier 在这 120 道题上的判定准确率和解析不了的条数；
- A、P 三个 seed 分开报，并报 3 个 seed 的平均（每道题先对 3 个 seed 的结果取平均，再算比例）；
- 区间：按状态（图）bootstrap 10,000 次，种子 1027，百分位法（重抽状态后用"和之比"算均值，同一组状态的所有读数用同一套重抽）；按源聚类只有 4 条验证源，只作参考。

## 4. 事先写定的读法（主读数是 S 闸门）

| 读法 | 条件 |
|---|---|
| `gate_prevents` | S 闸门下 G1 ≤ 0.15，且 G2 ≥ 0.85 × 无闸门的 G2 |
| `gate_costly` | G1 ≤ 0.15，但 G2 < 0.85 × 无闸门的 G2（拦得住，但误拦太多） |
| `gate_leaks` | G1 > 0.15 |

**预测**：`gate_prevents`。S5 在整个验证集上是 0.923，预期 G1 约 0.08，G2 约 0.9。A 在每个 seed 上都塌成一个常数，预期它要么全拦（G2 = 0），要么全放（G1 = 1）。

## 5. 局限

- 离线：只模拟"开始时判一次、不可行就停"，不测在线闸门的延迟（S 每次约 12 秒）、中途重判和停下之后的行为。
- 只有 60 个状态、4 条验证源；S 只有 1 个 seed；π0.5 每个条件只有 HIL 里的那一次执行。
- 60 个验证源状态全部是静置段（bin 0、1，布丁还没被拿起）；抓起段的 40 个状态都来自训练源，不在这次的题里。
- 验证集用于 S5、S4 的选模（按验证子集选更新步数），对 P、S 略有利；V5 的测试集已经用掉，干净的数字要等新的留出源（接手指南选项 2）。
- 结论只适用于直线规则、object/II/task1、π0.5。

## 6. 实现与资源

- 代码：`verifier_training/v5_gate_contract.py`（纯函数）、`v5_gate_run.py`（两个 CPU 阶段：preflight、report），启动器动作 `python -m verifier_training.launch_v5 gate --hil HIL --s3 S3 --s4 S4 --seeds SEEDS --s5 S5 --test TEST`（要求本协议已冻结、源码干净且已推送）；单元测试 `verifier_training/tests/test_v5_gate_contract.py`。
- 核对：
  - 启动器：各运行的阶段和链接关系（S4、加 seed、S5 都指向同一个 S3、S4），各前置作业 COMPLETED 0:0；A、P 的 6 个验证记录文件的哈希必须等于测试评估收据（`v5-test`）里记下的哈希（只读那份收据的哈希，不读测试结果）；收据记下每个证据文件的哈希；
  - preflight：先跑单元测试；每个证据文件的哈希等于收据；HIL 自己的 `HASHES.json` 核对通过，并从 `RUNS.jsonl.gz` 重算 R1、R2、R4，必须等于 `HIL_READING.json`；只按键对题（第 2 节），**不读任何判定**，写出 `preflight/QUESTIONS.json`；
  - report：重新对题并与 preflight 的题目逐项相同，读判定（重新解析核对）；S 的验证记录以前没有记过哈希，所以从整个记录文件重算 S 自己写的结论的准确率，必须等于 `S_seed713/RESULT.json` 和 `S5_READING.json`；写出 `GATE_READING.json`、`GATE_QUESTIONS.jsonl`。
- 只用 CPU，几分钟；在登录节点上只做轻量读取和单元测试，正式计算走 `short` 分区的作业，运行目录 `verifier_training/runs/<UTC>_v5-gate-offline_<commit>`。
- smoke：在草稿目录里走同样的两个阶段，收据里写 `smoke`（启动器不会写这一项）；smoke 的 report 不读判定，只算无闸门、真值、全部拦下三行。
- 先冻结本协议、再第一次读取判定字段。
