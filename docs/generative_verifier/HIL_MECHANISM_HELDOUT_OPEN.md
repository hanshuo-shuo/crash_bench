# 留出对开环定位：修复在别的任务对上为什么时灵时不灵

2026-11-05。接 [修复批次报告](HIL_MECHANISM_REPAIR_REPORT.md)的"下一步 2"。修复（amp2：第 12–14 层图像 token 上 K/V 的 B − A 放大到 2 倍）在留出任务对上只部分迁移：
- LIBERO-10 0→1 和 Goal 8→7 有效（每对失败格增益 +0.33）；
- LIBERO-10 1→0 很弱（+0.09），Object 1→0 完全无效（7 个臂都是 0/18）。

层窗口是在三对试点任务上选的。本批次只在存好的输入上做开环推理，回答"为什么弱"，从而决定下一步是换窗口、调剂量，还是停止修复、收尾写作。

## 1. 问题与假设

**问题**：修复在 LIBERO-10 1→0、Object 1→0 上弱，是因为
- **窗口不对**：这两对的 B 从一开始就不走第 12–14 层图像路；
- **推得不够**：路是同一条，但中途 B − A 太小，固定的 λ = 2 推不动；
- **没东西可推**：中途换成 B 后，第一个动作块和 A 几乎一样，B − A 放大了也没用；
- **还是第一个动作块以后的事**：路相同，推动也和有效的格差不多，弱的原因在后面的闭环过程或物理状态里。

对应的下一步：窗口不对 → 按对定位，再在那个窗口上做闭环；推得不够 → 留出剂量；后两种 → 不再追修复，收尾写作。

**顺带检验两件事**：
- 试点里"失败格图像 token 上的任务印记变淡"在留出对上是否也成立；
- 开环下 amp2 对第一个动作块的推动，能否预测闭环里修复的增益。如果能，以后选窗口、定剂量可以先在开环里筛。

**预先写下的预测**：
- H1 t = 0 的路：`shared`（试点三对的 E(第 12–14 层图像) 都在 0.51–0.55，Goodfire 在 DROID 上也是第 14–16 层）；
- H2 印记变淡：`image_route_fades`（修复批次里请求 1 的图像 V gap：留出失败格 0.36–0.48，成功格 0.75，起点格 0.71）；
- H3 开环推动能否预测闭环增益：不写预测；
- H4：LIBERO-10 1→0 读 `weak_push`，Object 1→0 读 `nothing_to_push`。两条都没有把握。

## 3. 每个状态测什么

**全套**（留出对），原样复用试点开环的 `run_open_loop.run_state`：
- 接口替换网格：单层和 3 层滑窗 × 全部 / 图像 / 文字 token，以及空替换和全替换；
- backbone 替换（每层的图像 token 残差；A、B 等长时加文字）；
- 每层的 gap（图像、文字）；
- 原生推理 3 次（A 孪生、A、B），以及试点的全部核对。

**新加：开环推动**（全部状态，包括校准）。用闭环里同一个程序（`Patcher.steer`），在存的输入上算请求 1：
- 对每个种子 s，噪声 key 取 `split(key(s))[1]`，即 `Policy.infer` 在重置到 s 后第一次请求用的 key；
- 四个动作块：
  - a = 指令 A、不动（λ = 1）；
  - b = 指令 B、不动；
  - amp2 = 指令 B，第 12–14 层图像 token 的 K/V 沿 B − A 再推一倍；
  - rand2 = 同样大小、随机方向，方向 key 与闭环 rand2 的请求 1 相同：`fold_in(key(direction_seed(SW)), 1)`。
- **推动** = E(amp2) − 1，E 用 a、b 两个块按试点的 path 公式算：0 = 和 b 一样，正数 = 比 b 更远离 a，单位是 ‖b − a‖。只在 a、b 相差 ≥ 3 个噪声底的种子上算，状态至少要 2 个这样的种子才算"可读"。
- 另记不归一化的推动大小：‖path(amp2) − path(b)‖ ÷ 噪声底。

## 5. 读法

第 5 节状态：已冻结（2026-11-05，提交前；冻结后读法和门槛不改）。

**只用正式批次的初始布置 2–19**，与修复批次正式运行的初始布置相同，所以每个状态都能和它在闭环里的结果配对。smoke 的初始布置 0、1 只作描述。

**记号**：
- W = 第 12–14 层、图像 token 的接口窗口（修复用的窗口）；
- E(W) = 只把 W 换成 B 的，动作往 B 靠了多少（试点的 E）；
- 格的值 = 状态值的中位数，95% 区间用 bootstrap 求（2000 次，种子 0）；
- 可读 = 试点的定义：E 至少在 2 个种子上有定义。

**C1 工具核对**（smoke 和正式都要过），`tool_ok` 需要以下全部成立：
1. 留出状态：试点 P1 的全部条件（`metrics.fidelity_reading`）。即重建的 B 输入哈希一致；空替换和 A 的差为 0；全替换的 E 在 1 ± 0.02 内；替换程序与原生的 path 差中位 ≤ 0.1 个噪声底、最大 ≤ 0.5；
2. 校准状态：重建的 B 输入哈希一致；
3. 全部状态：开环推动程序在 λ = 1 时，第一个种子的 a、b 与本作业 `Policy.infer` 的 L∞ 差中位 ≤ 0.01、最大 ≤ 0.05（闭环 C1 的门槛）；
4. 全部状态、每个种子：amp2 和 rand2 的 K/V 改动 ÷ ‖B − A‖ 与 1 的差 ≤ 0.001；
5. 全部状态：amp2 至少在一个种子上改变了动作块；
6. 每个分片都完成，每个状态的哈希核对通过，状态集合与计划一致。

**H1 t = 0 的路**（每个留出对的 f = 0 格）：
- `unreadable`：可读状态 < 5；
- `image_window`：E(W) 的格中位 ≥ 0.4；
- `elsewhere`：E(W) < 0.4，但某个 3 层窗口（任意起点，全部 / 图像 / 文字 token）的格中位 ≥ 0.4；
- `diffuse`：没有 3 层窗口 ≥ 0.4。

合起来：
- `insufficient`：可读的对 < 4；
- `shared`：每个可读的对都是 `image_window`；
- `differs`：其余情况。

0.4 是试点 P2 的 `interface_partial` 门槛。

**H2 印记变淡**（留出对的 .25 / .5 / .75 格）：
- 每个状态的 γ：第 12–17 层图像值向量 gap 的均值，除以同一对、同一初始布置在 f = 0 的值（试点的定义）；
- 失败格 = 修复批次的 commits 和 derails 格（8 格），成功格 = 修复批次的成功格（10 格）；
- 每类合并：类内各格状态合在一起取中位；区间用按格分层的 bootstrap（格内重抽状态）。

读法：
- `image_route_fades`：失败格中位 ≤ 0.8，上界 < 1，且成功格下界 ≥ 0.9；
- `image_route_kept`：失败格下界 ≥ 0.9；
- `mixed`：其余情况。

**H3 开环推动能否预测闭环增益**：
- **格**：13 个失败格，即试点失败格 5 个，加留出的 commits 和 derails 格 8 个。
- **每格两个量**：
  - S = 可读状态推动的中位；
  - G = 修复批次正式运行里同一批状态的 amp2 切换率减 native 切换率。
- **统计**：格间 Spearman ρ（同名次取平均名次）。区间用联合 bootstrap：每格内重抽状态，S 和 G 用同一组状态。有 S 的格少于 8 个时不读。

读法：
- `proxy_tracks`：ρ ≥ 0.5 且下界 > 0；
- `proxy_weak`：ρ > 0，其余情况；
- `proxy_fails`：ρ ≤ 0。

**H4 修复为什么弱**（每个"弱的对"读一次）：
- **有效 / 弱的划分**：用修复批次里每对失败格合并的增益 G（同上）。G ≥ 0.15（闭环的 GAIN）为有效，否则为弱。
  - 冻结的名单：有效 = 试点 7→8、2→9，留出 LIBERO-10 0→1、Goal 8→7；弱 = LIBERO-10 1→0、Object 1→0。
  - 汇总时由修复批次的运行记录重新算，与名单不一致就报错。
- **参照**：有效的对的 9 个失败格。
  - 参照可读率 = 这 9 格可读率（开环推动程序的可读）的中位；
  - 参照推动 = 这 9 格 S 的中位。
- **按顺序判**，取第一个成立的：
  1. `window`：这一对的 H1 是 `elsewhere` 或 `diffuse`。H1 是 `unreadable` 时这一条不可检，记下来，往下判；
  2. `nothing_to_push`：这一对失败格合并的可读率 < 参照可读率的一半；
  3. `weak_push`：这一对失败格合并的推动中位 < 参照推动的一半；
  4. `downstream`：其余情况。

**只报告、不作读数**：
- 每格的描述表：可读数、最佳单层、E(W)、最佳 3 层窗口（全部 / 图像 / 文字）、图像和文字 γ、开环推动可读率、推动和 rand2 推动、不归一化推动、闭环 native → amp2；
- 每个留出对 f = 0 的单层曲线和 backbone 曲线；
- H3 换成别的开环量：E(W)、图像 γ（试点格的这两个量取自试点开环正式批次的同一批状态）、rand2 推动，与 G 的 Spearman；
- 中间格的 γ；本作业原生输出与阶段 1 存档的跨作业数值差（B 的第一个动作块）。

**解读规则**（写在运行前）：
- **H1 `shared`**：B 在留出对上从一开始也走第 12–14 层图像路，"窗口只适合试点对"在 t = 0 不成立。
  **`differs`**：至少一对从一开始就走别的路，看是哪几对。
- **H2 `image_route_fades`**：试点的"失败格里图像印记变淡"推广到另外两个套件。
  **`mixed`**、**`image_route_kept`**：不推广，或只在部分对上成立。
- **H3 `proxy_tracks`**：开环推动能大致预测闭环增益，以后定窗口、定剂量可以先在开环里筛。
  **`proxy_fails`**：开环第一个动作块上看不出闭环效果，筛选必须做闭环。
- **H4**：
  - `window` → 下一步（要用户点头）：按对定位，再在那个窗口上闭环检验；
  - `weak_push` → 下一步（要用户点头）：留出剂量；
  - `nothing_to_push`、`downstream` → 不再追这一对的修复，作为修复的边界写进报告。

## 7. 风险

- **t = 0 可能读不出来**：试点 1→8 在 t = 0 只有 4/20 可读，因为 A、B 第一步都去抓碗。留出对里同样先去同一处的对，H1 会是 `unreadable`，这时 H4 第 1 条不可检。
- **只看第一个动作块**：开环推动只量请求 1，闭环效果还取决于后面几十次请求。H3 正是检验这一点；`downstream` 也就是"第一个动作块解释不了"。
- **格少**：H3 只有 13 格；H4 每个弱的对只有 1–3 格，Object 1→0 只有 18 个状态。
- **有效 / 弱的划分是在修复批次之后看出来的**：H4 只用它当标签，本批次的开环结果在冻结时还没看到。
- **跨作业数值噪声**：开环推动和修复批次闭环请求 1 的输入只有约一半逐位相同（EGL 渲染噪声），G 来自闭环，S 来自存的输入，只在格层面比较。
