# 从头不给任务信息：π0.5 的语言消融

2026-11-03。状态：已冻结。单元测试通过后、任何 GPU 执行前冻结设置和统计。
GPU smoke 仅检查管线；通过完整性 gate 后自动启动正式批次，不据 smoke 成功率修改设计。

## 1. 用户问题与授权

用户指出“回原点 / 停止 / 绕路”是训练分布外的命令，要求先在已有任务上把原指令
换成随机生成的 A、B、C、D、E、F、+，看看文字到底重不重要：
“在现有的任务上……给它一些 random 的指令……先做一个这样子的一个实验吧”。

本次执行范围：当前 π0.5 `pi05_libero`，原指令 / 空指令 / 随机字符，从 t = 0 起给定，
冻结设计，小规模管线 smoke、完整性 gate、正式评测和报告。标准 LIBERO 四套 40 个已有任务，
不改场景、不加任务，不训练、不接 verifier、不调付费 API。最多两张 A100。
本实验不读 SafeLIBERO 源轨迹或 V4/V5 锁定测试集。

## 2. 问题与边界

问的是：**缺少任务语言信息时，策略能否仍完成评测任务？**
这直接量化当前检查点在这些任务上的语言依赖程度。

- 原指令很好、空 / 随机文字很差：当前任务依赖语言，旧实验的命令分布外解释仍成立。
- 原指令和消融相近：在该套件中，场景 / 初始状态等线索足以支持大量任务完成。
- 各套件差别很大：按套件和任务解释，不能用总体均值说“VLA 不读文字”。

随机字符和空指令本身也分布外。性能下降可能同时受缺少任务信息和输入分布变化影响；
本实验不能证明理解或服从中途的新命令，也不能从成功率相近推出动作完全一样。
LIBERO-Goal 的同场景多目标结果应单独看；同场景中碰巧做了某个默认任务也可能被算成功。

## 3. 单元、提示与种子

- 标准 `libero_spatial / libero_object / libero_goal / libero_10`，基准顺序每套 10 个任务。
- 正式：每任务官方初始状态 0–9，共 400 个状态；不按原指令是否成功筛选。
- 三组，每个状态都跑：

| 条件 | 整次执行所用文字 |
|---|---|
| C0 | LIBERO 任务的原始英文句子 |
| EMPTY | 真正的空字符串 `""`，不替换成默认任务或额外说明 |
| RANDOM | 12 个独立均匀抽样的 `A B C D E F +` 符号，以单空格连接，无前缀或解释 |

- 随机文本种子：SHA256(`language-ablation-20261103|初始状态编号`)，Python `random.Random`。
  10 条随机字符串在所有任务上共用；同一初始状态编号对应同一条。
  字符串不编码任务或目标，文本种子与策略种子分开。完整字符串写入计划及 manifest。
- 策略种子沿用 `hil_suite.policy_seed(suite, task, init)`，三组及重复执行完全相同；
  每次执行前清空动作队列、重置策略 RNG，校验服务端确认。
- 每任务状态 0 再跑一次 C0（C0R），40 次，用来量渲染 / 执行噪声。
- 正式总计 **1,240 次**：400 × 3 + 40。没有新布局。
- smoke：四套各 task 0、官方状态 40，每状态三组 + C0R，共 16 次；
  与正式状态不重合，仅查管线，不进入正式统计。

## 4. 固定执行设置

完全复用已验证的 HIL suite 环境构建、图像 / 动作适配、策略服务和结果记录函数：

- LIBERO `8f1084e3132a39270c3a13ebe37270a43ece2a01`；
  openpi / AEGIS 上游 `2457feed5968ae803926e178c8ce8243b9ecdcf9`。
- `pi05_libero`，使用已暂存的同一公开检查点，manifest 记录路径。
- 环境种子 7，256 px，两张图旋转 180°，10 步空动作后才开始问策略。
- 每次执行 5 步动作块；步数上限依次为 220 / 280 / 300 / 520，三组相同。
- 原任务的官方 `done` 第一次为真时停止，否则跑满；不因消融而换评价目标。
- 各条件建独立环境，同一状态的各条件放在同一 GPU 分片；没有原指令前缀或中途切换。
- 校验原任务名 / 句子、实际服务端输入摘要、每次请求身份和 RNG。
  不在运行时给 EMPTY 补任何文字。记录实际提示 token 数，必须小于 200，无截断。

## 5. 完整性与停止规则

smoke 和正式汇总都要求：

1. 计划中全部执行齐全，无额外单元；任一步基础设施失败写 STOP，其余分片在下次执行前停止。
2. 每次记录连续步数、完整动作和物理哈希，重新算成功必须与记录一致。
3. 同一状态的起始物理哈希、本体输入和策略 RNG 键完全相同。
4. 图像沿用既有容差：最多 8 个灰度级、最多 0.1% 数值不同；超限即失败。
5. 三组第一次策略输入的摘要不同；C0R 可与 C0 相同。提示与计划逐字一致。
6. 报告 C0/C0R 成功一致数、逐步物理哈希一致数、末端最大偏差。

smoke 不按成功率挑参数或重选任务，不用它选择随机文本。正式结果不按 C0 成功与否排除。
任何错误修复都保留失败运行；新运行使用新根目录。源代码依赖作业结束前不改 / 同步仓库。

## 6. 预先固定的统计

- **主要读数**：每套件三组成功率，EMPTY − C0、RANDOM − C0 的配对百分点差。
- 另报：总体等任务权重均值，逐任务结果、消融 / C0 比值、
  C0 成功但消融失败及相反方向的计数、C0 成功状态中保留的成功数。
- 三组一起按每任务内的初始状态进行配对 bootstrap，任务权重相等，10,000 次，
  seed 1103，95% 百分位区间。任务集合固定，不把结果推广到任务总体；
  随机字符串银行本身的变化没有独立重复，区间不覆盖这种额外不确定性。
- C0 成功率为零的任务，比例不定义，照样报告差值和原始计数。
- C0R 只作噪声诊断，不进三组主读数。四个套件都报告，不只报差异最大的一套。
- 描述性消融，不加事后阈值或“听话 / 不听话”二分读法，不预测具体数字。
- 报告运行耗时、Slurm ID、代码 / 上游提交、全部种子、配置、输出重放、动作越界次数。
