# 退回再做：中途换不过去，有多少是因为"从当前状态够不着新任务"

2026-11-12，草稿；11-14 修订（U3 从读数降为只报告，见第 5 节）。这是[方法线计划](HIL_METHOD_PLAN.md)的第 1 步，接[任务对普查](HIL_MECHANISM_CENSUS.md)。

普查显示中途换指令在 90 对里大多失败（中途 22.8%，起点 98.0%），放大指令印记只把失败格从 8.0% 提到 13.1%。Causeway（arXiv 2609.30913）报告把手臂引到新任务的入口位姿后，π0.5 从 26.0% 到 61.6%。本批次用最简单的办法测同一件事：换指令时先用脚本放下手里的东西、退回本局的起始位姿，再让 π0.5 自己做新任务。

它有四个用处：给出上限；给出审稿人会要的最简单基线；证明这些中途状态下新任务做得成（普查缺的见证）；成功的轨迹可以当第 2 步训练的老师。

## 0. 批准与边界

- **用户**（11-12）：Claude 建议"先测'放下、退回起始位姿，再做 B'的上限，再做按机制设计的微调"，并说明第 1 步要新加脚本控制的退回动作、第 2 步要训练、两样都没批准过，"你点头的话，我把第 1 步写成方案"。用户："开始吧 然后看看我这地基稳不稳 然后开始进行plan的修正和下一个agent的说明"。
- **范围**：本方案、运行器里新增的脚本段、计划与汇总代码和测试、脚本段试跑、smoke、冻结、正式批次、报告。执行由下一个 agent 按用户的指示进行；指示里没提 GPU 时，提交第一条作业前向用户确认一句。
- **提交分两次**（第 3 节）：先单独提交 smoke；看过 smoke 后把脚本段常数和第 5 节冻结并提交；再提交"闸门 → 正式 → 汇总"这条链。
- **边界**：只用 π0.5（`pi05_libero`），标准 LIBERO-Goal 不改；不训练、不调付费 API、不碰 SafeLIBERO；最多两张 GPU。第 2 步（训练）不在本方案范围内，要用户另外点头。
- **停下来问用户**：闸门因非代码原因失败；U1 读成 `low`。

## 2. 设计

### 2.1 状态

普查正式批次的全部中途状态：90 个有序对 × 初始布置 0–9 × f = 0.5、0.75，共 1,764 个。前缀沿用普查的前缀根目录，不重跑；排除规则和协变量沿用普查的计划（`census.py`）。

前缀根目录（普查正式目录 `PLAN.json` 里的 `prefix_root`）：`/projects/p33100/siosio/crashbench_safelibero/mechanism/20261110T062727Z_mech-census-prefix_pi05_libero_d1f4b0269a0f`。

### 2.2 臂

| 臂 | 切换步上先做的脚本段 | 之后 |
|---|---|---|
| `home` | 张开夹爪 → 抬高 → 回到本局的起始位置和姿态 | π0.5 用指令 B，不做任何内部改动 |
| `release` | 张开夹爪 → 抬高 10 cm | 同上 |
| `native`（复核） | 无 | 同上；只在初始布置 5 的状态上重跑（约 176 个，十分之一），用来看和普查的一致程度 |

配对对照用普查里同一状态的 `native` 和 `amp2`，不整批重跑。

### 2.3 脚本段

沿用阶段 3 的 PUSH 写法（`hil_suite_run.py` 的 `perturb`）：每一步给环境一个 OSC 增量动作，裁剪到动作范围内，逐步记录并标记 `scripted`。

- **起始位姿**：本局等待步结束时（第 `WAIT` 步）末端的位置和姿态，在回放前缀时读出。
- **`home` 的三段**：
  1. 原地张开夹爪 10 步；
  2. 竖直抬到不低于起始高度；
  3. 位置和姿态同时向起始位姿做比例控制，直到位置误差 < 2 cm 且姿态误差 < 0.1 rad，或脚本段总步数到 80。
- **`release`**：第 1 段，再竖直抬高 10 cm 或到 30 步为止。
- 夹爪在整个脚本段保持张开指令。
- 没到达容差的运行不剔除，照常接着跑策略，计入分母；到达率单独报告。
- 夹爪张开是动作第 7 维取 −1（LIBERO 的约定；PUSH 的写法是沿用上一步的夹爪指令，这里不同）。写代码时在容器里确认方向。
- **常数怎么定**：增益、每步上限等在代码里写成具名常量。
  - 先做**脚本段试跑**：CPU 作业，在 LIBERO 容器里对十来个状态只跑回放和脚本段，不调策略、不占 GPU，用来调增益，直到位置和姿态都能在 80 步内到容差。
  - 再用 smoke 确认。smoke 里到达率不到 0.90 时可以再调常数、重跑 smoke。
  - 常数连同第 5 节一起冻结，写回本节。冻结之后不改。正式批次里到达率不到 0.90 算工具核对不通过，停下来问用户。

### 2.4 预算与成败

- 脚本段结束后给策略 300 步，与普查给的策略步数相同。同时报告"连脚本段在内 300 步以内完成"的比例。
- 成功 = 策略接手之后 B 的目标成立，判定方式与普查相同（遇到 B 成立即停；跨环境目标核对）。
- 脚本段结束时 B 已经成立的运行（比如松手时碗正好落在盘子上）不算策略的功劳：从 U1、U2、U4 和 U3 的分子和分母里都去掉，单独报告个数。
- 每次运行另记：是否把 A 做完；脚本段步数；脚本段结束时的位置和姿态误差；张开时手里是否夹着东西（普查的 `gripper_closed`）；A 和 B 的目标物体在脚本段前后的位移。

### 2.5 印记的读数

服务端的 native 程序本来就算新旧两条指令的缓存，并在日志里给出第 12–14 层图像 token 上的 gap = ‖V_B − V_A‖ / ‖V_B‖。本批次里策略的第一次请求发生在脚本段之后，所以：

- γ_post = 本批次请求 1 的 gap ÷ 普查里同一对、同一初始布置 f = 0 的 gap；
- γ_switch = 普查里同一状态 native 运行的 γ（退回之前）。

## 3. 规模与算力

- 正式：2 个臂 × 1,764 + 复核 176，约 3,700 次。普查每次约 22 秒，加上脚本段，估计约 25–30 GPU 小时；六个分片，同时最多两张 A100。
- smoke：初始布置 0，B = (A + 3) mod 10，两个时点，三个臂，约 60 次。
- 脚本段试跑：CPU，short 分区，十来个状态，几分钟。
- **提交顺序**：
  1. 脚本段试跑（CPU）。
  2. smoke（GPU，单独提交）→ 汇总 → 看 C1。
  3. 冻结常数和第 5 节，提交并推送。
  4. 一条链：闸门（在冻结后的代码上重算 smoke 的汇总，`tool_ok` 才放行）→ 正式 → 汇总。

## 4. 核对

**C1 工具核对**（smoke 和正式都要过），`tool_ok` 需要以下全部成立：

1. 每次运行都完成，哈希核对通过，结果能由轨迹重算出来；服务端日志与客户端逐请求一致；
2. 切换步的物理哈希与普查前缀磁带同一步相同；
3. 脚本段的每个动作都在动作范围内；脚本段步数不超过上限；`home` 到达容差的比例 ≥ 0.90；
4. 请求 1 上 native 程序与 `Policy.infer` 的 L∞ 差：中位 ≤ 0.01，最大 ≤ 0.05；没有任何 K/V 改动；
5. 实际用的指令都是 B；没有单元在切换步上 B 已成立；
6. 跨环境目标核对通过；
7. 运行器对原有条件（C0、SW、PUSH 等）的行为没有变化：单元测试里同一输入的动作序列逐位相同。

只报告：复核的 `native` 与普查同一状态结果一致的比例；脚本段结束时 B 已成立的运行数（应为 0，出现就单列）。

## 5. 读法

第 5 节状态：草稿（smoke 之后、提交"闸门 → 正式"那条链之前冻结；冻结后读法和门槛不改）。冻结时把这一行改成"第 5 节状态：已冻结（日期）"，启动器检查这几个字。

**单位与统计**：同普查。状态 = (A, B, 初始布置, 时点)；格的分类用普查的 native 成功率，已经固定（失败格 145、中间格 20、成功格 15）。两层 bootstrap（先重抽任务对，再在格内重抽状态），2000 次，种子 0。

**U1 上限**（主读数；**全部** 1,764 个中途状态，不按格挑），r = `home` 的 B 成功率：
- `high`：r ≥ 0.80；
- `moderate`：0.50 ≤ r < 0.80；
- `low`：r < 0.50。
- 可与同一批状态上的 native 22.8%、amp2 26.7% 直接比；同时报告 `home` − `native`、`home` − `amp2` 及区间。
- 不用失败格做主读数的原因：普查的格是按 native 的结果分的，在失败格上和 native 比会偏高（[地基审查](HIL_FOUNDATION_AUDIT.md)第 4 条）。失败格、成功格上的比例只报告。
- 预测：`moderate`，约 0.7。

**U2 只放下够不够**（失败格）：
- `pose_matters`：`home` − `release` ≥ 0.15 且区间下界 > 0；
- `release_enough`：`home` − `release` 的区间上界 < 0.15，且 `release` − `native` ≥ 0.15、区间下界 > 0；
- `unclear`：其余。
- 预测：`pose_matters`。

**U3 印记（只报告，不作读数；11-14 改）**（失败格，`home` 臂里到达容差的运行）：
- 每格取 γ_post 的中位数，再对格取中位数，连同区间报告；同时报告同一批状态的 γ_switch（普查失败格中位 0.66）。
- 为什么不作读数：π0.5 没有记忆，每一步只看当前画面、本体状态和指令。印记是同一张图配两条指令的差，完全由当前画面决定。手臂回到起始位姿、画面接近起点时，γ_post 接近 1 是意料之中，它说明不了"变淡是失败的原因"。
- 有信息量的是下面"只报告"里的一项：退回后的印记在不同物体的对里能不能区分成败。

**U4 代价**（普查的成功格，149 个状态），改变 = `home` − `native`：
- `harmless`：区间下界 ≥ −0.10；
- `costs`：区间上界 < 0 且改变 ≤ −0.10；
- `unclear`：其余。
- 预测：`harmless`。

**只报告、不作读数**：
- `home` 失败的运行里：又把 A 做完的、两个都没做成的各多少；按 same_object、`gripper_closed`、时点、B 的目标物体是否被移动分组的成功率；
- `home` 臂里 γ_post 对成败的 AUROC，全部、同一物体的对、不同物体的对分开报（普查里 γ 在不同物体的对中只有 0.555）；
- `home`、`release` 失败的运行里，末端到过 B 干活位置 8 cm 以内的比例（定义同 `experiments/mechanism/census_reach_posthoc.py`；普查里不干预、照旧做完 A 的运行是 24%，换成功的是 99%）；
- 每个任务对的成功率分布（零成功的对有几个；普查里 native 是 36 个）；
- 脚本段步数、到达率、连脚本段在内 300 步以内完成的比例。

**解读规则**（写在运行前）：
- **U1 `high` 或 `moderate`**：这些中途状态下，场景本身允许做 B，模型也会做 B；中途换不过去是因为手臂所处的状态，不是因为新任务做不成。支持第 2 步用 `home` 的成功轨迹当老师。它不说明模型在原来的状态下"听见了"新指令。
- 要不要把"保住印记"的损失当一个消融臂，只看退回后的印记能否在不同物体的对里区分成败（只报告项），见[计划](HIL_METHOD_PLAN.md)第 2.4 节。
- **U1 `low`**：退回到起始位姿也救不回来（比如 A 做到一半已经改变了场景）。这个老师不能用，停下来问用户。
- **U2 `release_enough`**：衔接动作可以很短，第 2 步的数据好造；`pose_matters`：位姿要紧，和 Causeway 的结论一致。
- **U4 `costs`**：不能无条件退回；第 2 步要让模型自己学会什么时候不用退（同物体的对）。
- 本批次的 `home` 用了本局的起始位姿和仿真里的脚本控制，是上限和老师，不是要发表的方法。Causeway 在 OpenVLA-OFT 上有同一类参考值（把手臂直接放到入口状态，79.2%），报告里并排列出。

服务端用现有的 `serve_steer.py`，臂是 `native`，不改。

**实现时要注意的几处**（11-12 冷读代码时发现的）：

1. **不要把新条件加进 `PERTURB`**（`hil_suite.py`）。那个字典同时驱动阶段 3 的计划，加进去会改变已完成批次的计划。另设一个集合，在 `run_branch` 里单独分支。
2. **脚本段的记录要带目标判定**。现在 PUSH 的记录是 `record(..., {})`，`others` 是空的；`hil_suite.py` 的 `first` 在设了 B 的时候会因此报 KeyError。新脚本段每一步都要带上 `checkers`。
3. **预算**。`run_branch` 里策略的终点是 `checkpoint + budget`，脚本段的步数算在里面。新条件要改成"脚本段结束后再给 300 步"。
4. **起始姿态磁带里没有**。前缀磁带只存了末端位置。起始位置和姿态都在回放到第 `WAIT`（10）步时从环境的观测里读。
5. **先写保护测试**。`perturb` 现在没有任何测试。动它之前先存一份 PUSH 的动作序列当基准，改完后逐位比对。
6. **测试怎么跑**见[计划](HIL_METHOD_PLAN.md)第 0 节的操作备忘。

**测试**：位姿误差到动作的函数（裁剪、容差、终止、姿态误差的符号）；计划的计数、排除规则与普查一致、复核子集；U1、U2、U4 在几种设定世界里的标签；C1；假运行目录上的汇总和闸门；原有条件的动作序列逐位不变。LIBERO 环境只在容器里有，脚本段和真实环境的配合由 smoke 检验。

## 7. 风险

- **放下时东西会掉**：夹着碗或酒瓶时张开夹爪，物体会从空中掉落，可能滚开或倒下。这是这个最简单做法的真实代价，记录位移，按是否夹着东西分组报告。
- **姿态控制**：A 是拧旋钮、开抽屉一类任务时，末端姿态偏得多，80 步内可能回不到容差。到达率进 C1。
- **场景已经被 A 改了**：A 做到一半可能已经挪动了 B 要用的物体。这类失败是真实的，单列报告。
- **每个状态一个策略种子，而且重跑会翻**：同样的状态、种子和臂重跑，失败格里约 11–19% 的状态结果不同（GPU 推理不逐位相同，闭环会放大）。格和任务对一级的比例是稳的。所以读数按任务对重抽汇总，不解读单个状态；1/10 的 native 复核用来报告这个翻转率。
- **它同时是可行性见证**：现象那一条最大的漏洞是没人证明"这个中途状态下 B 做得成"。`home` 做成了，就说明场景本身允许做 B，失败出在手臂所处的状态。报告里把这层意思写明。
- **与文献数字不能直接比**：Causeway 用的是 71 个跨物体对、第 30 / 60 步和完成后三个时点。报告里并排列出时注明差别。
