同步规则由 [scripts/quest_sync.sh](../scripts/quest_sync.sh) 实现：本地 clean commit 必须先 push 到 upstream，Quest 也必须 clean，然后 Quest 只通过 `git fetch` + `git merge --ff-only` 到完全相同的 commit。它不会使用 `rsync --delete`，不会触碰 Quest 的 `envs/`、`third_party/`、模型缓存、视频和 activation。

日常命令：

```bash
scripts/quest_sync.sh status
scripts/quest_sync.sh dry-run
scripts/quest_sync.sh push
scripts/quest_sync.sh queue
scripts/quest_sync.sh exec 'REMOTE COMMAND'
scripts/quest_sync.sh pull-result results/path/to/file-or-directory
```

本地改代码后的完整顺序必须是：测试 → commit → `git push` → `scripts/quest_sync.sh push` → `scripts/quest_sync.sh status`。不要直接 rsync 源码到 Quest，否则 paper-facing provenance 会失真。

## 已解决的问题

1. macOS 系统 Bash 不支持 `declare -A`：提交脚本已改为兼容旧 Bash。
2. GitHub push 曾因远端领先被拒：已整理到当前线性分支，不要 force-push。
3. Slurm 报 `No module named numpy`：实际原因是作业调用了系统 Python；所有 P0 sbatch 现固定调用 `$HOME/crash_bench/envs/openvla/bin/python`。
4. `module purge` 后 provenance 找不到 `git`：`crashbench/provenance.py` 支持 `CB_GIT_EXECUTABLE`，所有 P0 sbatch 显式加载 `git/2.47.0-gcc-12.4.0` 并记录版本。
5. GPU 节点不存在 `/usr/bin/git`：不再硬编码该登录节点路径，而是从已加载 module 动态解析。
6. `DependencyNeverSatisfied`：这是上游 gate 失败后的正常 Slurm 结果，不是 scheduler 永久卡住；上游修复后重新提交整条链。
7. 源码 rsync 会让 Quest HEAD 与运行代码不一致：同步工具已改为 exact Git fast-forward。
8. `pull-result` 拉目录曾产生重复嵌套目录：已改为区分远端文件/目录并保持路径结构。

从 capture 开始直到 guard 完成：

- 不要执行 `scripts/quest_sync.sh push`；
- 不要在 Quest checkout 中改文件或恢复 stash；
- 不要切分支；
- 可以继续在本地开发，但不要同步到 Quest；
- 如果 capture 失败，下游出现 `DependencyNeverSatisfied` 时，先读 capture log，不要直接重提下游。

guard 会核对 capture 的 Git commit；中途改变 Quest HEAD 会使 guard fail closed。
